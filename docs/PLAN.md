1. 목표와 범위

영상의 나무 코스(경사 트랙 → 쐐기 → 볼링핀 → 소용돌이 → 결승선)를 재현한 3D 구슬 경주 추첨 게임을 웹으로 만든다. 모바일 브라우저에서 60fps, 초기 다운로드 gzip 1.0MB 이하가 기준이다.

2. 기술 스택

Three.js(WebGLRenderer) + Rapier 3D 0.19.3 + TypeScript + Vite로 만든다. 같은 조합으로 3D 구슬 경주를 구현한 공개 저장소가 4개 이상 있고, 예상 합계는 gzip 약 0.9~0.95MB다.

Rapier를 0.19.3에 고정하는 이유

0.20 이상에는 스텝당 회전각 상한(약 45° = π/4)이 있다. 미끄러짐 없이 구르는 구슬의 속도 상한은 다음과 같다.

v = \frac{\pi r}{4\,\Delta t}

반지름 r = 8mm, Δt = 1/120초이면 v = 0.754 m/s다. 경사 6° 트랙 1m를 내려온 구슬의 속도가 1.21 m/s이므로 첫 경사로에서 이미 상한에 걸린다. 0.21은 번들도 약 63% 커졌다는 서드파티 측정이 있다.

고르지 않은 것

cannon-es: 마지막 릴리스가 2022-08-12이고 CCD가 없다. 앞서 대화에서 제가 가벼운 대안으로 언급했지만, 조사 결과 유지보수가 멈춰 있어 제외한다.

JoltPhysics.js: 약 0.9MB(gzip)로 더 크고, three.js와 함께 쓴 구슬 경주 선례가 적다.

React Three Fiber: React 런타임이 추가된다.

3. 아키텍처

경주 로직(race/, physics/, map/, rng.ts)은 DOM과 three.js를 전혀 참조하지 않게 분리한다. 그래야 Node에서 화면 없이 1,000시드를 돌려 수치로 튜닝할 수 있다.

4. 코스 설계

코스는 출발 게이트 → 지그재그 경사 트랙 3단 → 쐐기 구간 → 볼링핀 구간 → 소용돌이 → 결승선 순서로 위에서 아래로 이어진다. 치수는 스크린샷에서 짐작한 추정치이고 헤드리스 시뮬레이션으로 조정한다.

공통 원칙은 하나다. 평평한 면과 난간은 전부 직육면체(cuboid) 충돌체로 만들고, 트라이메시는 소용돌이 한 곳에만 쓴다. 트라이메시 삼각형 이음새에서 구슬이 튀는 문제가 생기지 않는다.

트랙 폭은 조사 보고서의 30mm가 아니라 150mm로 잡았다. 스크린샷에서 지름 16mm 구슬 5개와 쐐기가 한 판 위에 나란히 있기 때문이다(5 × 16mm = 80mm).

경사 트랙의 속도

미끄러짐 없이 구르는 속이 찬 구의 가속도는 다음과 같다.

a = \frac{5}{7}\, g \sin\theta

θ = 6°이면 a = 0.714 × 9.81 × 0.1045 = 0.732 m/s²이다. 정지 상태에서 0.8m를 내려오면 v = √(2 × 0.732 × 0.8) = 1.08 m/s다.

터널링 조건

한 스텝 이동량 v·DT가 (구슬 반지름 + 판 두께의 절반)보다 작아야 한다. 최고 속도 3 m/s, DT = 1/240초이면 이동량은 12.5mm이고 한계는 8 + 5 = 13mm다. 여유가 0.5mm뿐이므로 바닥 판 충돌체는 아래쪽으로 30mm까지 두껍게 만든다(렌더 메시는 10mm 그대로).

소용돌이

원뿔 면에서 반지름 R의 원 괤도를 유지하는 속도는 다음과 같다(마찰을 무시한 근사).

v = \sqrt{g R \tan\alpha}

R = 0.15m, α = 20°이면 v = √(9.81 × 0.15 × 0.364) = 0.73 m/s다. 마찰과 구름 저항이 에너지를 빼앗아 R이 줄면서 나선을 그리며 내려간다. 둘레를 N분할했을 때 다각형 면과 실제 원의 최대 차이는 R·(1 − cos(π/N))이고, N = 72이면 0.14mm(구슬 반지름의 1.8%)다.

맵 데이터

코스는 코드가 아니라 public/maps/wood-v1.json으로 정의한다. 조각 종류는 ramp, drop, wedge, pins, funnel, finish 6가지다.

3단계

결승 판정

스텝 해상도는 1/240초 = 4.17ms다. 같은 스텝에 두 구슬이 들어오면 결승 평면까지의 부호 거리로 스텝 사이를 선형 보간해 순서를 가른다. 그래도 같으면 시드 난수로 정한다.

공정성

출발 슬롯이 균등 무작위로 배정되면, 코스가 특정 슬롯에 유리하더라도 이름별 당첨 확률은 1/n이다. 코스 편향은 따로 측정한다. 헤드리스로 M = 1,000시드를 돌려 슬롯별 우승 횟수 O를 세고, 기대값 E = M/n과 비교한다.

\chi^2 = \sum \frac{(O - E)^2}{E}

n = 5이면 E = 200, 자유도 4, 유의수준 0.05의 임계값은 9.49다. 이 값을 넘으면 쐐기 위치를 조정한다.

재현 범위

"같은 빌드 + 같은 시드 = 같은 결과"까지만 약속한다. 기기가 다를 때도 비트 단위로 같은지는 확인되지 않았다.

6. 성능 전략

강체가 15개(구슬 5 + 핀 10) 수준이라 물리 비용은 작다. 가벼움은 다운로드 용량과 드로콜 수에서 결정된다.

볼링핀, 소용돌이, 구름 저항 토크, 끼임 안전망, sim/headless.ts, 녹화

1,000시드에서 χ² < 9.49. 경주 시간 중앙값 30~45초. 미완주 구슬 0개

3. 확장

다중 맵, 맵 에디터, Multiple 당첨, 가중치, 스킬, 리플레이 공유

맵 JSON만 바꿔 새 코스가 실행됨

4. 선택

WebGPU 렌더러 옵션, Rapier 0.21 이상으로 이전

각속도 상한과 번들 크기 문제가 해소된 경우에만 진행

8. Claude Code 작업 방법

빈 폴더에 이 문서를 docs/PLAN.md로 저장하고, 아래 내용을 CLAUDE.md로 둔 뒤 단계별 프롬프트를 하나씩 실행한다. 한 단계가 완료 기준을 통과하면 커밋하고 다음 단계로 간다.

CLAUDE.md

# 3D 구슬 경주 웹 게임설계 문서: docs/PLAN.md (작업 전 해당 단계 섹션을 읽을 것)## 스택- TypeScript + Vite, three (WebGLRenderer), @dimforge/rapier3d 0.19.3 (버전 고정, 올리지 말 것)- UI는 프레임워크 없이 DOM 직접 조작- 테스트: Vitest## 명령- npm run dev      개발 서버- npm run build    빌드 후 dist 의 gzip 크기 출력- npm run test     단위 테스트- npm run sim -- --seeds 1000   헤드리스 시뮬레이션## 규칙- src/race, src/physics, src/map, src/rng.ts 는 DOM, three 를 import 하지 않는다- 물리 스텝은 고정 1/240초. 경주 시간은 스텝 번호로 센다 (Date, performance.now 금지)- 시뮬레이션에 영향을 주는 난수는 rng.ts 의 시드 PRNG 만 쓴다 (Math.random 금지)- 단위: 1 unit = 0.1m, 중력 98.1 units/s^2, 구슬 반지름 0.08 unit- 평면과 난간은 cuboid, 쐐기는 convexHull. trimesh 는 소용돌이에만 쓰고 FIX_INTERNAL_EDGES 를 켠다- 코스 치수는 코드에 쓰지 말고 public/maps/*.json 에 둔다- 물리 값을 바꾸면 npm run sim 으로 완주율과 카이제곱 값을 다시 확인한다- 빌드 결과 gzip 합계 1.0MB 이하를 유지한다

단계별 프롬프트

0단계

docs/PLAN.md의 2, 3절과 7절 0단계를 읽고 프로젝트를 초기화해줘. config.ts, rng.ts, physics/world.ts를 만들고, 경사판 1개와 구슬 1개를 Node에서 돌리는 Vitest 테스트로 0단계 완료 기준 3가지를 검증해줘. 화면은 아직 만들지 마.

1단계, 물리와 경주 로직

PLAN.md 4절의 맵 JSON 스키마대로 map/schema.ts, map/build.ts를 만들고 public/maps/wood-v1.json에 경사 트랙 3단, 쐐기 6개, 결승선을 정의해줘. race/race.ts에 출발 게이트, 진행도, 순위, 결승 판정을 구현하고, 같은 시드로 두 번 돌린 순위가 같은지 테스트해줘.

1단계, 화면

render/scene.ts, render/camera.ts, ui/를 만들어줘. PLAN.md 6절의 드로콜·그림자·해상도 방침을 따르고, 이름 입력(이름*개수), 셔플, 시작, First/Last, ?seed= 공유, 순위 오버레이를 넣어줘. 끝나면 npm run build로 gzip 크기를 보고해줘.

2단계

볼링핀과 소용돌이 조각, physics/rolling.ts의 구름 저항 토크, 끼임 안전망을 추가해줘. sim/headless.ts로 1,000시드를 돌려 슬롯별 우승 횟수, 카이제곱 값, 경주 시간 중앙값, 미완주 수를 출력하고, 완료 기준을 맞출 때까지 맵 JSON 값을 조정해줘.

작업할 때 지킬 것

물리 값 튜닝은 눈으로 보지 말고 npm run sim 수치로 판단하게 한다. Claude Code가 스스로 실행하고 검증할 수 있다.

화면 확인은 폰 실기기에서 직접 한다. npm run dev -- --host로 같은 와이파이의 폰에서 접속한다.

참고 구현이 필요하면 rotsch/MarbleRace의 physics.js, race.js, sim.mjs 구조를 보게 한다. 코드를 가져올 때는 해당 저장소의 라이선스를 먼저 확인한다.

10. 수익화

무료 기본 게임에 유료 맵·꾸미기 판매와 직접 광고 문의를 중심에 두고, 광고 네트워크는 보조로 붙인다. 한 번 방문에 30~45초만 쓰는 추첨 도구라서 광고 노출만으로는 수익이 작다.

방법

구조

확인된 수치·조건

맵·스킨 판매

기본 맵 무료, 추가 맵·구슬 스킨·로고 삽입을 유료로 판매

마블 룰렛이 상점 사이트로 맵 추가 버튼을 연결해 두었다. 유료 여부는 페이지에 명시되지 않았다

직접 광고·스폰서

코스 벽면이나 결승 화면에 광고주 로고 노출

마블 룰렛에 광고문의 링크가 있다

구글 H5 Games Ads

경주 사이 전면 광고, 보상형 광고

신청 후 승인제, 승인된 애드센스 계정 필요. 전면 광고 간격은 120~240초가 표준

카카오 애드핏

이름 입력 화면에 배너

웹 매체 등록 후 광고 호출이 발생하면 심사. 지급 요청은 5만원 이상부터

게임 포털 입점

포털에 올리고 광고 수익 배분

개발자 몫: itch.io 90%, CrazyGames 광고 60%·구매 70%, Poki 50%. Poki는 5년 웹 독점이 기본

보상형 광고 eCPM 기준치는 미국 $15~28, EU $8~15, 인도·브라질 $1~3이다. 한국 수치는 찾지 못했다.

수익 계산식

광고 수익 = 월 세션 수 × 세션당 광고 노출 수 × eCPM ÷ 1000

광고: 월 10만 세션, 세션당 1회 노출, eCPM $5로 가정하면 100,000 × 1 × 5 ÷ 1000 = $500

판매: 같은 트래픽에서 맵 1개 3,000원, 구매 전환율 0.5%로 가정하면 100,000 × 0.005 × 3,000 = 150만 원

두 경우 모두 가정값이고, 실제 수치는 출시 후 측정한다.

설계 원칙

유료 요소는 당첨 확률에 영향을 주지 않는다. 맵, 구슬 색, 로고 같은 외형만 판매한다.

보상형 광고의 보상은 스킨 해금 정도로 한정한다. 구글 정책상 금전 가치가 있는 보상과 "후원해 주세요" 같은 시청 유도 문구는 금지다.

경주 화면에는 배너를 넣지 않는다. 드로콜과 프레임 예산을 지키고 녹화 영상에 광고가 찍히지 않게 한다.

맵과 스킨은 JSON과 텍스처 파일로 분리돼 있어, 판매용 콘텐츠를 코드 수정 없이 추가할 수 있다.
